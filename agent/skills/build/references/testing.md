# Shared testing policy

Use this policy when planning, writing or reviewing tests. Reading it does not start build or any other stage workflow; the active stage keeps its own planning, audit and reporting duties. Honor explicit project checks and test constraints; surface conflicts rather than ignoring them.

**Maximize confidence per scenario, not test count.** Every changed test must protect a named behavior and catch a plausible regression that cheaper retained coverage misses. Retained coverage may suffice.

- **Start at the caller.** Exercise the entry point real callers use, with realistic inputs and real internal collaborators. Assert returned results, persisted state/readback or consequential effects. For substantial browser-facing workflows, prefer one representative existing Playwright/system scenario spanning navigation, actions and persisted outcome. Keep backend-only contracts and detailed permutations in focused integration tests; do not duplicate them across layers.
- **Mock external boundaries, not the claimed behavior.** Stub third-party HTTP, vendor SDKs and genuinely external effects—not internal decisions, writers or orchestration whose correctness the scenario claims to establish. Avoid copied implementations, vacuous records and negative assertions made inevitable by a stub. Name the realistic wrong behavior that would fail the assertion and check that setup/mocks do not bypass it. Avoid assertions tied to harmless refactoring; use controlled clocks.
- **Cover distinct outcomes.** Select representative success, meaningful failure and applicable authorization/transaction/retry scenarios. Distinguish supported actors, client types and versions where semantics differ; prove changed consumer decisions through those consumers. Preserve distinct rollback, security/privacy, partial-effect (including external effects), compatibility and wrong-actor protection. Exhaustive permutations belong in focused tests only when complex logic genuinely needs them, with real inputs and outputs.
- **Make focused tests earn their place.** Complex logic merits focused tests when they protect a distinct regression that caller-level scenarios do not adequately cover; purity is not the criterion. There is no file-per-class requirement. Coverage percentages, test-to-code ratios, convention alone and “new code needs tests” do not justify additions.
- **Keep one owner per contract.** Extend retained scenarios or add a few assertions before adding files, fixture-heavy setups, suites or shared harnesses. Do not repeat the same guarantee at every layer. Name retained or replacement coverage before consolidating or deleting tests; deletion is not automatic. Choose the smallest correction that retains distinct protection.
- **Do not test incidental observability.** Logger calls/wording, metric names/tags and payload shapes need an explicit acceptance criterion or consequential consumer, such as an alert, security audit record or functional payload contract. Assert that contract in an existing real scenario rather than a mock-only shape matrix. An observability-only deliverable can qualify, but not every emitted field needs a test.
- **Automate what can be proved reliably.** Replace repetitive local manual checks with repeatable caller-to-outcome coverage where reliable. Distinguish mocked regressions from real integration evidence. Do not claim absolute confidence or skip necessary browser, integration or production-specific verification; report the remaining gap.
